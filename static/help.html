Three ways to use the UI
  1. Live — collector writes to SQLite; dashboard reads the growing database (tail mode).
  2. Export playback — load a JSON bundle in the browser; nothing is written to the DB.
  3. Guided capture — CLI records a clean session folder for bug reports.

Evidence Doctor

On the dashboard, set the time window (presets or From/To), then click Analyze range (or open Analysis). You get deterministic findings: Framework #146 shape, thermal vs power-cap signals, missing PMF, and related evidence.

Live DB: GET /api/findings. Loaded export: POST /api/analyze/export in the browser only (nothing is uploaded).

CLI: framelog analyze export.json (--format json, --output, --ai-prompt).

Export limits

Dashboard Export window and GET /api/export are limited to 7 days and 500k samples. For full history use framelog dump or a capture folder.

Throttle flags in plain English

Each flag means firmware or hardware says "slow down for this reason" at that moment. A flag does not say how much performance was lost; it tells you which limit was active.

Good references: AMD SMI’s GPU violations page explains indep_throttle_status, and the Linux kernel AMDGPU gpu_metrics docs explain the sysfs data source.

Power limits

FlagPlain meaning
SPLSocket/package power limit. Often the important one for Framework #146: the APU package is being held to a long-term power cap.
SPPTA longer running power budget is active, so clocks may stay lower until average power drops.
FPPTA short burst power budget is active; this often appears during quick spikes.
SPPT_APUSustained power budget for the APU side specifically.
PPT0–PPT3Firmware-defined package power budgets. The number is an internal slot; use nearby PMF limits and power readings to interpret it.
APCCPlatform controller requested a power limit. Think "the laptop platform is asking the chip to back off."
PPMPlatform power management limit. A board, firmware, or OS policy is limiting power.
FITReliability protection. Firmware is limiting boost to stay inside lifetime/aging safety rules.

Thermal limits

FlagPlain meaning
PROCHOT_CPUCPU hot/throttle signal. The CPU side reports it is hot enough, or externally told, to reduce performance.
PROCHOT_GPUGPU hot/throttle signal. The graphics side reports a thermal throttle condition.
TEMP_HOTSPOTThe hottest sensor on the GPU/APU reached its limit. This can be higher than the average or edge temperature.
TEMP_CORECPU/APU core temperature limit.
TEMP_GPUGPU temperature limit.
TEMP_EDGEGPU edge temperature limit, usually a sensor near the edge of the die.
TEMP_MEMGraphics memory temperature limit.
TEMP_SOCSystem-on-chip temperature limit.
TEMP_VR_GFX, TEMP_VR_SOC, TEMP_VR_MEM0, TEMP_VR_MEM1Voltage regulator temperature limits. Power delivery parts are hot, not necessarily the silicon itself.
TEMP_LIQUID0, TEMP_LIQUID1Liquid-cooling sensor limits. Usually irrelevant on a laptop unless firmware exposes placeholder bits.
VRHOT0, VRHOT1Voltage regulator "hot" signals. The power delivery hardware is asking for reduced load.

Current limits

FlagPlain meaning
TDC_GFXSustained graphics current limit. The graphics rail is drawing too much current over time.
TDC_SOCSustained SoC current limit.
TDC_MEMSustained memory current limit.
TDC_VDDSustained core-voltage current limit.
TDC_CVIPSustained current limit for AMD's CVIP block, when present.
EDC_CPUShort spike CPU current limit. A brief current burst exceeded the safe boost envelope.
EDC_GFXShort spike graphics current limit.

Live inspection

While framelog run or framelog.service is active, open the dashboard. Use Tail (live) and Refresh to follow new samples.

The UI is read-only for telemetry. framelog inspect prints one sample to the terminal only.

Export playback

No separate playback daemon. Run framelog serve without a collector, then Load export and choose export.json.

framelog serve --db /path/to/framelog.db

The status banner switches to export mode; charts use the file in your browser only. Use Return to live on the dashboard to read the SQLite database again.

Guided capture

Best for Framework issue #146.

capture and reset --yes fail while the DB is still receiving samples. Stop framelog.service (or any collector on the same --db) and wait ~5s if you just stopped it.

1. Stop the service

sudo systemctl stop framelog.service

2. Run capture

framelog capture --duration 20m --issue framework-146
framelog-capture-framework-146-<timestamp>/
  export.json
  analysis.json
  manifest.json
  system.json
  report.md
  summary.txt
  pre_capture_backup.json   # unless --skip-pre-backup

3. Inspect offline

framelog serve
# Load export → export.json

4. Optional dump / reset

framelog dump --output-dir ~/exports
framelog reset --yes --backup-dir ~/exports

CLI commands

CommandPurpose
runCollector + web UI (systemd default)
collectCollector only
serveWeb UI only
inspectCapabilities probe + one live sample (JSON)
capabilitiesHardware signals, recommended collector, Evidence Doctor rules
captureBackup, reset, collect, export folder
dumpJSON export from DB (no web limits)
analyzeFindings from export.json
reset --yesClear telemetry (backup first)

Global flags: --db, --interval-ms, --bind, journal window, --apu-only, --collector (lib-amdgpu, intel, fake, amdgpu-top-json). On Intel Framework laptops use --collector intel; AMD throttle/SPL rules do not apply. GET /api/capabilities mirrors the CLI probe. See the README compatibility table.

After capture

sudo systemctl start framelog.service

The capture folder on disk is independent of restarting the service.
